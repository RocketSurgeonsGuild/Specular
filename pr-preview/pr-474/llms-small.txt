# Specular

> Compile-time assembly scanning for .NET. AOT-safe, zero runtime reflection.

AOT & Trim Safe Generated code requires zero runtime reflection — fully compatible with .NET Native AOT and IL trimming. Build-Time Scanning A Roslyn incremental source generator resolves selector expressions at compile time and emits a strongly-typed `ISpecularProvider`. Drop-In for Scrutor Familiar fluent selector API — `FromAssemblyOf<T>()`, `AddClasses()`, `AsMatchingInterface()` — but evaluated at build time.

# Cross-Assembly Caching

> How Specular caches what it learns about referenced assemblies in SpecularProvider.ctpjson, and when a cached entry is used.

# Cross-Assembly Caching [Section titled “Cross-Assembly Caching”](#cross-assembly-caching) ## The problem [Section titled “The problem”](#the-problem) A project’s selectors usually reach into referenced assemblies: `FromAssemblies()`, `DependenciesFromAssemblyOf<T>()` and the like walk every type of every matching reference. Referenced assemblies rarely change between builds of the project that uses them, so walking them again on every build is wasted work, and in a large solution it is most of the generator’s time. ## What Specular caches [Section titled “What Specular caches”](#what-specular-caches) Specular keeps one cache file per project, `obj/ctp/SpecularProvider.ctpjson`, and stores in it what it learned about each **referenced** assembly on the last build. The project’s own types are never cached: they are what you are editing. The file is written and read by the [`Specular.Scanning`](../../guide/scanning-from-your-generator/) library that Specular’s generator is built on, under the consumer id `SpecularProvider`. It holds three kinds of entry, each stored per referenced assembly: | Entry | What it holds | | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | Scan results | For each selector’s assembly and type filters, the types they matched in the assembly. Keyed by the request’s [cache key](../scan-cache-file/#shape). | | `requests` | The selectors a referenced assembly carries for its consumers: Specular records each library’s own `GetTypes` and `Scan` calls on the library as `[assembly: AssemblyMetadata]`, and re-runs them against the consuming project. Decoding those attributes is cached here, even when there are none. | | `sources/<key>` | The code a call site generated for the assembly. The key hashes the whole call-site location, the request it resolved to, and whether the build targets Native AOT, so two identical call sites in different projects never share an entry. | Generated code that reported diagnostics is never cached, so diagnostics always come from a fresh run. The file’s layout is described in [The scan cache file](../scan-cache-file/). ## When an entry is used [Section titled “When an entry is used”](#when-an-entry-is-used) Every entry is tied to the referenced assembly’s **module version id (MVID)**, which the compiler changes whenever the assembly’s contents change. An entry is used only while the MVID it was stored with matches the reference’s current one: * A referenced assembly that was rebuilt with any change gets a new MVID, so all of its entries miss and it is walked again. * A reference without a readable MVID is never cached. In the IDE, project references are live compilations rather than built files, so they are always walked; while you type, results are reused in memory for as long as the reference is unchanged instead. * A cache file written by an older version of the format is ignored and rebuilt. * Only entries used in a build are written back, so entries for removed references and selectors drop out. The file is written only when its content changes, so an unchanged cache doesn’t touch the project’s up-to-date check. ## How the file gets back to the compiler [Section titled “How the file gets back to the compiler”](#how-the-file-gets-back-to-the-compiler) `Specular.targets` imports `Specular.Scanning.Cache.targets`, which, just before `CoreCompile`, adds every existing `obj/ctp/*.ctpjson` to the compilation as an additional file, and deletes them on `Clean`. The generator finds its own file by name. Nothing needs configuring. ## Two-project example [Section titled “Two-project example”](#two-project-example) 
```mermaid
sequenceDiagram
    participant Lib as Lib (referenced)
    participant App as App build
    participant Cache as App/obj/ctp/SpecularProvider.ctpjson


    Note over App,Cache: First build
    App->>Lib: Walk Lib's types for each selector
    App->>Cache: Save scan results, requests and generated code, keyed by Lib's MVID


    Note over App,Cache: App changes, Lib doesn't
    Cache->>App: Fed back as an additional file
    App->>App: Lib's MVID matches: reuse its entries, walk only App's own types


    Note over Lib: Lib changes and is rebuilt (new MVID)
    Cache->>App: Fed back as an additional file
    App->>App: MVID differs: entries miss, walk Lib again
    App->>Cache: Save the new entries
```
 ## Failure modes [Section titled “Failure modes”](#failure-modes) | Situation | Behaviour | | ------------------------------------------------------------------- | ----------------------------------------------------------------------------- | | The file is missing, empty, corrupt, or from another format version | Treated as empty: every referenced assembly is walked and the file rewritten. | | A referenced assembly changed since the entry was written | Its entries miss and it is walked again. | | The file can’t be written (read-only `obj/`, IO error) | Ignored; the build succeeds and the next build walks again. | | The build runs outside MSBuild (no `IntermediateOutputPath`) | Nothing is written. | In every case the build produces the same output as an uncached build: the cache only saves work. ## `SpecularHashAttribute` [Section titled “SpecularHashAttribute”](#specularhashattribute) Specular still stamps each assembly it generates for with `[assembly: SpecularHashAttribute("…")]`, a hash of the generated provider. It is no longer used to validate the cache, which relies on MVIDs.

# How It Works

> A conceptual overview of the Roslyn source generator pipeline that powers Specular's compile-time assembly scanning.

# How It Works [Section titled “How It Works”](#how-it-works) Specular replaces runtime reflection-based assembly scanning with a **Roslyn `IIncrementalGenerator`** that runs during your build. By the time your application starts, all type and assembly scan results are pre-computed and baked into generated C# — there is nothing to resolve at runtime. ## Overview [Section titled “Overview”](#overview) When you write code like this: 
```csharp
provider.GetTypes(s => s.FromAssemblyOf<MyService>().AddClasses().AsMatchingInterface())
```
 Specular’s generator finds that call during compilation, evaluates the selector expression against the Roslyn symbol graph, and emits a concrete implementation that returns the pre-computed results directly. No reflection, no startup cost, and full AOT/trimming compatibility. ## The Three Syntax Providers [Section titled “The Three Syntax Providers”](#the-three-syntax-providers) `SpecularProviderGenerator` (in `CompiledTypeProviderGenerator.cs`) registers three distinct syntax providers during `Initialize`, one for each method on `ISpecularProvider`: | Syntax Provider | Handles | | ----------------------------- | -------------------------------------- | | `AssemblyCollection` | `provider.GetAssemblies(…)` call sites | | `ReflectionCollection` | `provider.GetTypes(…)` call sites | | `ServiceDescriptorCollection` | `provider.Scan(…)` call sites | Each provider scans the syntax tree for its corresponding method invocation, extracts the selector expression, and passes it downstream for resolution. ## Call Site Detection [Section titled “Call Site Detection”](#call-site-detection) Each `ISpecularProvider` method carries hidden compiler-injected parameters: 
```csharp
IEnumerable<Type> GetTypes(
    Func<IReflectionTypeSelector, IEnumerable<Type>> selector,
    [CallerLineNumber]   int lineNumber = 0,
    [CallerFilePath]     string filePath = "",
    [CallerArgumentExpression(nameof(selector))] string argumentExpression = ""
);
```
 The `[CallerArgumentExpression]` attribute causes the compiler to pass the **literal text of the selector lambda** as a string. The generator reads that text and hashes it with `GetArgumentExpressionHash`, which normalises whitespace before computing an MD5 hash. This hash is the stable key that links a specific call site to its generated output — change the lambda text and the hash changes, triggering re-generation. ## Symbol Visitor Walk [Section titled “Symbol Visitor Walk”](#symbol-visitor-walk) For each call site, the generator resolves which types satisfy the selector by walking the Roslyn `ITypeSymbol` graph. The `AssemblyProviders/` directory contains the visitors and compiled filters that do this work: * **`TypeSymbolVisitor`** — walks the type hierarchy of an assembly, accumulating matching `INamedTypeSymbol` instances. It exposes `GetReferencedTypes` (walks all referenced assemblies) and `GetCompilationTypes` (walks the current compilation only). * **`CompiledTypeFilter` / `CompiledAssemblyFilter`** — evaluate individual filter predicates: namespace scoping, type kind (class, interface, enum…), attribute presence, assignability to a base type or interface, and name patterns. * **`FindTypeVisitor` / `FindTypeInAssembly`** — locate specific types needed for assignability checks across assembly boundaries. The net result is a precise, build-time enumeration of every type that would have been returned by the equivalent runtime reflection call. ## Code Emission [Section titled “Code Emission”](#code-emission) After resolving all call sites, the generator builds a single `SpecularProvider.g.cs` file containing: 1. A concrete class that implements `ISpecularProvider`, with each method returning a hard-coded collection for its call-site hash. 2. An `[assembly: SpecularHashAttribute("…hash…")]` attribute that embeds a hash of the generated provider. Cached results for referenced assemblies are validated by their MVIDs instead; see [Cross-Assembly Caching](../cross-assembly-caching/). The generated provider is exposed through the static `SpecularProvider.Instance` property — you call into it directly, with zero reflection scanning. ## Incremental Rebuild [Section titled “Incremental Rebuild”](#incremental-rebuild) Because Specular uses Roslyn’s `IIncrementalGenerator` API, the pipeline is fully incremental. Call sites whose selector expression text has not changed produce no re-computation. Only modified selectors, or changes to the types a selector matches, cause re-emission. In large solutions this means the generator adds negligible time to incremental builds. ## Pipeline Diagram [Section titled “Pipeline Diagram”](#pipeline-diagram) 
```mermaid
flowchart TD
    A[User calls provider.GetTypes&#40;selector&#41;] --> B[Roslyn IIncrementalGenerator]
    B --> C{Three Syntax Providers}
    C -->|GetAssemblies| D[AssemblyCollection]
    C -->|GetTypes| E[ReflectionCollection]
    C -->|Scan| F[ServiceDescriptorCollection]
    D & E & F --> G[Hash selector expression at call site]
    G --> H[Symbol visitor walks ITypeSymbol graph]
    H --> I[Apply compiled filters]
    I --> J[Emit SpecularProvider.g.cs]
    J --> K[Zero reflection at runtime]
```
 ## Next Steps [Section titled “Next Steps”](#next-steps) To understand how scan results are shared across project references without redundant symbol resolution, see [Cross-Assembly Caching](./cross-assembly-caching.md). To list every discovered scanner expression, assembly, and type as compile-time metadata (plus a Mermaid diagram of the same data), see [Scan Report](./scan-report.md).

# Scan cache file

> The shape of the .ctpjson file Specular.Scanning writes for each generator, and the rules that decide when its entries are used.

# Scan cache file [Section titled “Scan cache file”](#scan-cache-file) Generators built on [`Specular.Scanning`](../../guide/scanning-from-your-generator/) keep their results for referenced assemblies in one file per generator: `$(IntermediateOutputPath)ctp/<ConsumerId>.ctpjson`. This page describes what the file holds and when its entries are used. You don’t need to read or write it yourself; the format is internal and may change between versions. ## Lifecycle [Section titled “Lifecycle”](#lifecycle) 
```plaintext
build N    generator scans  ──►  writes obj/…/ctp/<ConsumerId>.ctpjson   (only if the content changed)
build N+1  MSBuild adds ctp/*.ctpjson to AdditionalFiles before CoreCompile
           generator reads its own file  ──►  reuses entries whose MVID still matches
                                         ──►  rescans the rest, writes the file again
clean      MSBuild deletes ctp/*.ctpjson
```
 * The generator picks out its file by name: `<ConsumerId>.ctpjson`, ignoring case. Every generator gets its own file, so generators never read each other’s entries. * `context.Scan` writes the file from an implementation-only output step, so the IDE never writes it. A generator that saves a typed store with `ScanCache.Save` decides where it saves. Either way the file is written only when its content changes, which keeps its timestamp, and with it the project’s up-to-date check, stable. * The MSBuild wiring that feeds the file back (`Specular.Scanning.Cache.targets`) ships in every generator package packed with the library. See [Packaging and MSBuild](../../guide/scanning-from-your-generator/#packaging-and-msbuild). ## Shape [Section titled “Shape”](#shape) The file is compact JSON, written on one line. Laid out: 
```json
{
    "schema": 2,
    "scans": {
        "<request key>": {
            "MyLib": {
                "mvid": "6f9619ff-8b86-d011-b42d-00c04fc964ff",
                "types": [
                    { "name": "MyLib.FirstPlugin", "fullyQualifiedName": "global::MyLib.FirstPlugin", "kind": 2, "access": 6, "accessible": true },
                    { "name": "MyLib.Outer+NestedPlugin", "fullyQualifiedName": "global::MyLib.Outer.NestedPlugin", "kind": 2, "access": 4 }
                ]
            }
        }
    },
    "store": {
        "<store key>": {
            "MyLib": { "mvid": "6f9619ff-8b86-d011-b42d-00c04fc964ff", "version": 1, "data": { "name": "First" } }
        }
    }
}
```
 | Field | Meaning | | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `schema` | The file format version. A file with any other version is ignored and rebuilt. | | `scans` | The types each request matched in each referenced assembly: request key, then assembly metadata name. | | `scans.<key>.<assembly>.mvid` | The module version id of the assembly when the entry was written. | | `scans.<key>.<assembly>.types[]` | The matched types: `name` (full metadata name), `fullyQualifiedName` (the C# name, `global::`-qualified; an entry without it is a miss), `kind` (Roslyn `TypeKind`), `access` (Roslyn `Accessibility`), `accessible` (whether the consuming compilation can reference it), `arity`, and `assembly` when it differs from the entry’s assembly. | | `store` | The values a generator stored with `ScanCache.Set`: the generator’s key, then assembly metadata name. | | `store.<key>.<assembly>.mvid`, `version` | The assembly’s MVID and the generator’s data version when the value was written. | | `store.<key>.<assembly>.data` | The value, serialized with the generator’s `JsonTypeInfo<T>`. | Enums are written as numbers. Default values (`false`, `0`, `null`) are left out. Keys are written in ordinal order, so the same entries always produce the same bytes. The request key is `ScanRequest.CacheKey`: a SHA-256 hash, in base64url, of a canonical text form of the request. That form includes every assembly and type clause, and for each custom filter its class name and its `CacheKey`. The key is stable across processes and builds, and changes whenever the request changes. ## When an entry is used [Section titled “When an entry is used”](#when-an-entry-is-used) | Situation | Result | | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | | The referenced assembly’s MVID matches the entry’s | The entry is used; the assembly isn’t walked. | | The MVID differs (the assembly was rebuilt with different content) | The entry is ignored; the assembly is walked and the entry replaced. | | The reference has no readable MVID (an IDE project reference) | Never cached on disk; always walked. In-memory reuse still applies. | | The compilation’s own assembly | Never cached; always walked. | | A typed-store value with a different data version | A miss. | | A typed-store value that no longer deserializes into the generator’s type | A miss. | | The file is missing, empty, corrupt or has another `schema` | Treated as empty; everything is rescanned and the file rewritten. | | An entry wasn’t read or written during the run | Dropped when the file is saved, so entries for removed references and requests disappear. | | The file can’t be written (locked, no permission) | Ignored; the next build rescans. The cache never fails a build. | ## In memory [Section titled “In memory”](#in-memory) The disk file only helps across builds. Within one process, such as the IDE while you type, `context.Scan` also remembers each referenced assembly’s results for as long as the compiler keeps the same metadata reference object. An edit to the project’s own code then rescans only the project’s own assembly. These results are kept per consuming assembly, because accessibility depends on who is looking. ## Specular’s own file [Section titled “Specular’s own file”](#speculars-own-file) Specular’s generator uses consumer id `SpecularProvider`, so its file keeps the name `SpecularProvider.ctpjson`. What it stores is described in [Cross-Assembly Caching](../cross-assembly-caching/).

# Scan Report

> Access compile-time Specular scan results through the generated SpecularScanReport API.

# Scan Report [Section titled “Scan Report”](#scan-report) Specular generates a public `SpecularScanReport` class alongside `SpecularProvider`. Its `GetScanResults()` method returns a `Specular.Diagnostics.ScanResults` value containing every assembly, type, and service-descriptor scan resolved during compilation. 
```csharp
var results = SpecularScanReport.GetScanResults();
```
 Each report includes the name of the assembly that defined the scan expression and its selector expression normalized to one line. The result collections are grouped by scan kind: * `AssemblyScanReports` lists the selected assemblies. * `TypeScanReports` groups selected types by every assembly that was scanned. An assembly remains in the report even when no types matched. * `ServiceDescriptorScanReports` groups emitted service descriptors by every assembly that was scanned. Each descriptor carries its effective `ServiceLifetime`, registered service type name, and implementation type name. Empty scan results are retained. The report is pure compile-time metadata: it does not perform reflection or add trim/AOT requirements. It is suitable for tooling such as an external Mermaid renderer. ## Opting Out [Section titled “Opting Out”](#opting-out) Scan reports are generated by default. Disable them with: 
```xml
<PropertyGroup>
  <SpecularGenerateDiagnostics>false</SpecularGenerateDiagnostics>
</PropertyGroup>
```

# What is Specular?

> Specular is a compile-time assembly scanning library for .NET that replaces runtime reflection with Roslyn source generation.

# What is Specular? [Section titled “What is Specular?”](#what-is-specular) ## The Problem: Runtime Reflection at Startup [Section titled “The Problem: Runtime Reflection at Startup”](#the-problem-runtime-reflection-at-startup) Libraries like [Scrutor](https://github.com/khellang/Scrutor) make it easy to wire up dependency injection by scanning assemblies at startup: 
```csharp
services.Scan(scan => scan
    .FromAssemblyOf<Program>()
    .AddClasses()
    .AsMatchingInterface());
```
 This is convenient, but it comes with real costs: * **Startup latency** — every call to `Assembly.GetTypes()` allocates and reflects over metadata at runtime. * **AOT / IL trimming incompatibility** — the .NET Native AOT compiler and the IL trimmer cannot statically determine which types will be loaded via reflection, so they must either keep everything (bloating the binary) or trim too aggressively (causing runtime failures). `Assembly.GetTypes()` is flagged as trim-unsafe. * **No compile-time errors** — a misconfigured selector silently produces wrong registrations; you only find out at runtime. ## The Solution: Compile-Time Scanning [Section titled “The Solution: Compile-Time Scanning”](#the-solution-compile-time-scanning) Specular moves the scan to **build time**. A [Roslyn incremental source generator](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/source-generators-overview) reads the same fluent selector expressions you already write, evaluates them against the compilation’s type graph, and emits a strongly-typed `ISpecularProvider` implementation whose methods return **pre-computed, hard-coded arrays** — no reflection required at runtime. 
```plaintext
[Build time]
selector expression  ──►  Roslyn generator  ──►  SpecularProvider.g.cs
                                                   (pre-resolved type lists)


[Runtime]
ISpecularProvider.GetTypes(...)  ──►  returns the pre-built array  ──►  zero reflection
```
 The generated file is checked into `obj/` and compiled into your assembly just like any other C# source file. The runtime cost of a scan drops to an array return. ## Key Concepts [Section titled “Key Concepts”](#key-concepts) ### `ISpecularProvider` — the generated entry point [Section titled “ISpecularProvider — the generated entry point”](#ispecularprovider--the-generated-entry-point) `ISpecularProvider` is the interface your code calls. It exposes three methods: | Method | What it returns | | -------------------------- | ---------------------------------------------------------- | | `GetAssemblies(selector)` | Assemblies matched by the selector | | `GetTypes(selector)` | Types matched by the selector | | `Scan(services, selector)` | Registers matched types directly into `IServiceCollection` | The static property `SpecularProvider.Instance` exposes the generated provider for the entry assembly. See [Quickstart](./quickstart/) for usage. ### Selector Expressions [Section titled “Selector Expressions”](#selector-expressions) Selectors are the fluent lambdas you pass to each method: 
```csharp
provider.GetTypes(s =>
    s.FromAssemblyOf<Program>()
     .AddClasses()
     .AsImplementedInterfaces())
```
 The generator captures the **text** of the lambda via `[CallerArgumentExpression]` and hashes it to produce a stable key. Each unique selector expression at each call site generates a distinct result set. Changing the selector — even whitespace-significantly — causes the generator to re-evaluate and re-emit. ### `SpecularProvider.ctpjson` — Cross-Assembly Cache [Section titled “SpecularProvider.ctpjson — Cross-Assembly Cache”](#specularproviderctpjson--cross-assembly-cache) When the generator processes an assembly it writes a cache file (`SpecularProvider.ctpjson`) alongside the output. Downstream assemblies that reference yours can consume this cache instead of re-resolving all types from scratch, keeping incremental builds fast. ## Comparison to Scrutor [Section titled “Comparison to Scrutor”](#comparison-to-scrutor) Scrutor walks your assemblies at runtime using `Assembly.GetTypes()`, `Type.IsAssignableTo()`, and similar reflection APIs. This is flexible and works in all .NET environments, but it cannot be used with Native AOT and incurs startup cost proportional to the number of types in scope. Specular performs the same logical scan at **compile time** using Roslyn’s type symbol graph. The runtime implementation is a generated class that returns a pre-computed array — there is no reflection, no assembly enumeration, and no trim warnings. The trade-off is that Specular requires a build step and that selector changes require a recompile (which is already true for all source-generated code). ## Next Steps [Section titled “Next Steps”](#next-steps) * [Installation](./installation/) — add Specular to your project in under 5 minutes * [Scanning from your own generator](./scanning-from-your-generator/) — use Specular’s compile-time scanner, with its build cache, in your own source generator ## Contributing to the Docs [Section titled “Contributing to the Docs”](#contributing-to-the-docs) If you are editing documentation, install the VS Code recommended extensions for the best authoring experience: * **Astro** (`astro-build.astro-vscode`) — syntax highlighting and IntelliSense for `.astro` and `.mdx` files * **Starlight Links** (`hideoo.starlight-links`) — link autocomplete and validation for `docs/src/content/docs/` paths VS Code will prompt you to install these automatically when you open the `docs/` folder. Accept the prompt or install them via the Extensions panel.

# AOT Publishing

> Publish your Specular-powered app with .NET Native AOT — zero trim warnings.

# AOT Publishing [Section titled “AOT Publishing”](#aot-publishing) ## Why AOT Compatibility Matters [Section titled “Why AOT Compatibility Matters”](#why-aot-compatibility-matters) .NET Native AOT compiles your application to a standalone native binary at publish time. The IL trimmer removes all code that is not statically reachable from the entry point. Both transformations fail — or produce incorrect binaries — when application code calls trim-unsafe APIs. The most common source of trim warnings in DI-heavy applications is assembly scanning: 
```plaintext
ILLink: Trim analysis warning IL2026: 'Assembly.GetTypes()' requires unreferenced code.
```
 Standard runtime scanners (including Scrutor) call `Assembly.GetTypes()` at startup. The trimmer cannot know at publish time which types will be returned, so it cannot safely remove any of them — or it warns that it might. ## How Specular Avoids This [Section titled “How Specular Avoids This”](#how-specular-avoids-this) Specular’s generator resolves every scan at **build time**, before the trimmer or AOT compiler ever runs. The generated `SpecularProvider.g.cs` contains only direct `typeof()` expressions and array literals: 
```csharp
// Generated — no reflection APIs
return new Type[] { typeof(MyService), typeof(OtherService), typeof(ThirdService) };
```
 `typeof()` is a compile-time constant. The trimmer sees it as a static root, keeps the referenced types, and produces no warnings. There are no calls to `Assembly.GetTypes()`, `Type.GetMethod()`, `Activator.CreateInstance()`, or any other dynamically-dispatched reflection API in the Specular runtime path. ## Supported Target Frameworks [Section titled “Supported Target Frameworks”](#supported-target-frameworks) Specular targets `net10.0` and `net11.0` — both of which support Native AOT publishing. The `net11.0` build is compiled with runtime async. ## Publishing Command [Section titled “Publishing Command”](#publishing-command) 
```bash
dotnet publish -r linux-x64 --self-contained -p:PublishAot=true
```
 Replace `linux-x64` with your target runtime identifier (`win-x64`, `osx-arm64`, etc.). For a Release build: 
```bash
dotnet publish -c Release -r linux-x64 --self-contained -p:PublishAot=true
```
 ## Verifying Zero Trim Warnings [Section titled “Verifying Zero Trim Warnings”](#verifying-zero-trim-warnings) After publishing, check the output for any trim warnings that mention Specular: 
```bash
dotnet publish -r linux-x64 --self-contained -p:PublishAot=true 2>&1 | grep -i specular
```
 A clean Specular integration produces no output from that command. If you see trim warnings, they originate from your own code or from other dependencies — not from Specular itself. You can also enable verbose trim analysis to get a full report: 
```xml
<!-- in your .csproj -->
<PropertyGroup>
    <TrimmerRootDescriptor>TrimmerRoots.xml</TrimmerRootDescriptor>
    <SuppressTrimAnalysisWarnings>false</SuppressTrimAnalysisWarnings>
</PropertyGroup>
```
 ## Trim-Safe Patterns with Specular [Section titled “Trim-Safe Patterns with Specular”](#trim-safe-patterns-with-specular) ### Use `[ServiceRegistration]` instead of convention-based scanning where possible [Section titled “Use \[ServiceRegistration\] instead of convention-based scanning where possible”](#use-serviceregistration-instead-of-convention-based-scanning-where-possible) `[ServiceRegistration]` attributes are read at **compile time** by the generator. The generated code contains explicit `typeof()` references — the trimmer keeps the marked types automatically. 
```csharp
// Trim-safe: generator emits typeof(OrderService) directly
[ServiceRegistration<IOrderService>(ServiceLifetime.Singleton)]
public class OrderService : IOrderService { }
```
 ### Keep selectors stable across builds [Section titled “Keep selectors stable across builds”](#keep-selectors-stable-across-builds) Because selectors are hashed by their text, avoid dynamically constructing selector strings or conditionally branching on environment variables inside selectors. The generator evaluates selectors once at build time — the result is fixed until the next build. ### Avoid `FromAssemblies()` in AOT scenarios [Section titled “Avoid FromAssemblies() in AOT scenarios”](#avoid-fromassemblies-in-aot-scenarios) `FromAssemblies()` includes all assemblies loaded at the time the generator runs. In an AOT binary, the set of assemblies is fixed at publish time, so this works correctly. However, it can slow incremental builds when the dependency graph is large. Prefer `FromAssemblyOf<T>()` for tighter scoping. ## Next Steps [Section titled “Next Steps”](#next-steps) Explore the Reference section for the full selector API, lifetime configuration, and cross-assembly cache details.

# Installation

> Add Specular to your .NET project in under 5 minutes.

# Installation [Section titled “Installation”](#installation) ## Prerequisites [Section titled “Prerequisites”](#prerequisites) * .NET 10 or .NET 11 SDK * A project that uses `Microsoft.Extensions.DependencyInjection` ## 1. Add the NuGet Package [Section titled “1. Add the NuGet Package”](#1-add-the-nuget-package) 
```bash
dotnet add package Specular
```
 Or add it manually to your `.csproj`: 
```xml
<ItemGroup>
    <PackageReference Include="Specular" />
</ItemGroup>
```
 > **Central Package Management:** If your solution uses `Directory.Packages.props`, add the version there and reference it without a version attribute in the project file: > > ```xml > <!-- Directory.Packages.props --> > <PackageVersion Include="Specular" Version="x.y.z" /> > ``` ## 2. No Attribute to Apply [Section titled “2. No Attribute to Apply”](#2-no-attribute-to-apply) There is nothing to wire up by hand. When the generator runs it stamps your assembly with `[assembly: SpecularHashAttribute("<hash>")]` automatically (a hash of the generated provider) and emits the `SpecularProvider` class you scan through. You never write this attribute yourself. > **Libraries that are only scanned** — and never call `ISpecularProvider` themselves — can opt out of emitting their own provider by setting `<SpecularEmitProvider>false</SpecularEmitProvider>` in the project file. Application and entry projects emit a provider by default. ## 3. Build the Project [Section titled “3. Build the Project”](#3-build-the-project) 
```bash
dotnet build
```
 The Roslyn incremental source generator runs automatically during the build. After a successful build, the generated provider appears under your project’s `obj/` folder: 
```plaintext

  Debug/
    net10.0/

```
 You can inspect `SpecularProvider.g.cs` to see exactly what the generator produced — a concrete class implementing `ISpecularProvider` whose methods return pre-computed arrays of types. ## 4. Verify the Setup [Section titled “4. Verify the Setup”](#4-verify-the-setup) Add a quick check to confirm the provider resolves: 
```csharp

Console.WriteLine(provider.GetType().FullName); // should print "SpecularProvider"
```
 ## No Additional Configuration [Section titled “No Additional Configuration”](#no-additional-configuration) That’s it. The generator runs automatically on every build. There are no config files and no additional packages to reference. The only optional MSBuild knobs are `<SpecularEmitProvider>` (see step 2) for libraries that should not emit their own provider, and `<SpecularGenerateDiagnostics>false</SpecularGenerateDiagnostics>` to opt out of the [scan report](../architecture/scan-report.md) (on by default). The `SpecularProvider.ctpjson` cache file is written to `obj/ctp/` and fed back to the next build of the same project automatically, so referenced assemblies that haven’t changed aren’t scanned again (see [Cross-Assembly Caching](../architecture/cross-assembly-caching.md)). ## Next Steps [Section titled “Next Steps”](#next-steps) * [Quickstart](../quickstart/) — write your first selector and register services

# Quickstart [Section titled “Quickstart”](#quickstart) This page assumes you have already [installed Specular](../installation/). ## 1. Obtain the Provider [Section titled “1. Obtain the Provider”](#1-obtain-the-provider) The generator emits an `SpecularProvider` class into your assembly and exposes it through the static `SpecularProvider.Instance` property: 
```csharp
ISpecularProvider provider = SpecularProvider.Instance;
```
 `SpecularProvider` is `internal`, so `Instance` is available throughout your project. You can hold it in a variable or field, or call it inline — `ISpecularProvider` is a plain interface you can also inject. ## 2. Scan for Types [Section titled “2. Scan for Types”](#2-scan-for-types) Call `GetTypes()` with a fluent selector. The selector is a lambda whose text the generator captures at build time via `[CallerArgumentExpression]`: 
```csharp
IEnumerable<Type> types = provider.GetTypes(s =>
    s.FromAssemblyOf<Program>()
     .AddClasses()
     .AsImplementedInterfaces());
```
 The full selector fluent API is covered in the Reference section. Common starting points: | Selector step | What it does | | --------------------------------- | -------------------------------------------------- | | `FromAssemblyOf<T>()` | Scope the scan to the assembly containing `T` | | `FromAssemblies()` | Include all loaded assemblies | | `DependenciesFromAssemblyOf<T>()` | Include assemblies that reference `T`’s assembly | | `AddClasses()` | Filter to concrete (non-abstract) classes | | `GetTypes()` | Return all matched types without further filtering | ## 3. Register with Dependency Injection [Section titled “3. Register with Dependency Injection”](#3-register-with-dependency-injection) ### Option A — `Scan()` directly into `IServiceCollection` [Section titled “Option A — Scan() directly into IServiceCollection”](#option-a--scan-directly-into-iservicecollection) `ISpecularProvider.Scan()` combines the scan and registration in one call: Program.cs 
```csharp
var builder = WebApplication.CreateBuilder(args);
var provider = SpecularProvider.Instance;


provider.Scan(builder.Services, s =>
    s.FromAssemblyOf<Program>()
     .AddClasses()
     .AsImplementedInterfaces()
     .WithSingletonLifetime());
```
 ### Option B — `AddSpecularServiceRegistrations()` [Section titled “Option B — AddSpecularServiceRegistrations()”](#option-b--addspecularserviceregistrations) `AddSpecularServiceRegistrations` is an `IServiceCollection` extension method that reads `[ServiceRegistration]` attributes applied directly to classes and registers them according to their declared lifetime: 
```csharp
// On your service class:
[ServiceRegistration<IMyService>(ServiceLifetime.Singleton)]
public class MyService : IMyService { }


// In Program.cs:
builder.Services.AddSpecularServiceRegistrations(provider);
```
 The signature is: 
```csharp
public static IServiceCollection AddSpecularServiceRegistrations(
    this IServiceCollection services,
    ISpecularProvider provider);
```
 ## 4. What the Generated Code Looks Like [Section titled “4. What the Generated Code Looks Like”](#4-what-the-generated-code-looks-like) Conceptually, the generator emits something like this (simplified): 
```csharp
// SpecularProvider.g.cs  — auto-generated, do not edit
internal sealed class SpecularProvider : ISpecularProvider
{
    public IEnumerable<Type> GetTypes(
        Func<IReflectionTypeSelector, IEnumerable<Type>> selector,
        int lineNumber = 0,
        string filePath = "",
        string argumentExpression = "")
    {
        // Hash of "s => s.FromAssemblyOf<Program>().AddClasses().AsImplementedInterfaces()"

    }
    // ...
}
```
 There are no calls to `Assembly.GetTypes()`, no reflection, and no dictionary lookups over runtime metadata. Every result is a compile-time constant array. ## 5. You can read the selector expressions below to understand how scanning resolves **without running anything** — that is the whole point of a compile-time provider. ## The three libraries [Section titled “The three libraries”](#the-three-libraries) Each library is a plain class library that references `Specular`. Interface-matching, Singleton (Catalog) [Section titled “1. Interface-matching, Singleton (Catalog)”](#1-interface-matching-singleton-catalog) 
```csharp
provider.Scan(
    services,
    z => z.FromAssemblyOf<IProductService>()
          .AddClasses(f => f.InExactNamespaceOf<IProductService>())
          .AsMatchingInterface()
          .WithSingletonLifetime()
);
```
 `AsMatchingInterface()` registers `ProductService` as `IProductService`, `CategoryService` as `ICategoryService`, and so on. ### 2. Attribute-based, Transient as-self (Notifications) [Section titled “2. Attribute-based, Transient as-self (Notifications)”](#2-attribute-based-transient-as-self-notifications) 
```csharp
provider.Scan(
    services,
    z => z.FromAssemblyOf<NotificationDispatcher>()
          .AddClasses(f => f.WithAttribute<ServiceRegistrationAttribute>())
          .AsSelf()
          .WithTransientLifetime()
);
```
 Only types carrying `[ServiceRegistration]` are registered, each as its own concrete type. ### 3. Interface-matching with an opt-out, Scoped (Diagnostics) [Section titled “3. Interface-matching with an opt-out, Scoped (Diagnostics)”](#3-interface-matching-with-an-opt-out-scoped-diagnostics) 
```csharp
provider.Scan(
    services,
    z => z.FromAssemblyOf<IHealthCheck>()
          .AddClasses(f => f.WithoutAttribute<ExcludeFromSampleScanAttribute>())
          .AsMatchingInterface()
          .WithScopedLifetime()
);
```

# Scanning from your own generator

> Use Specular.Scanning to give your own Roslyn source generator Specular's compile-time assembly and type scanning, with results cached across builds.

# Scanning from your own generator [Section titled “Scanning from your own generator”](#scanning-from-your-own-generator) Specular’s generator scans assemblies and types at build time. `Specular.Scanning` makes that scanner available to your own Roslyn incremental source generator. You describe a scan with a symbol-based copy of Specular’s runtime selectors (`FromAssemblies().GetTypes(f => f.AssignableTo(...))`), run it inside your pipeline, and get back an equatable result. Results for referenced assemblies are cached: in memory while the IDE edits the project, and on disk across builds. This page is for **source generator authors**. If you only want to register services or find types in an application, use `Specular` itself; see the [Quickstart](../quickstart/). ## Choosing a package [Section titled “Choosing a package”](#choosing-a-package) The library ships in two forms with the same code and API, in the `Specular.Scanning` namespace. | Package | What your generator gets | Choose it when | | --------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | | `Specular.Scanning` | A compile reference to `Specular.Scanning.dll`, which is packed beside it. | You want the simplest setup. This is the default. | | `Specular.Scanning.Sources` | The library’s `.cs` files compiled into your generator as `internal` types. | You don’t want a second assembly loaded beside your generator, or you need to be sure no other generator’s copy can clash with yours. | With the DLL package, every generator that uses the library ships its own `Specular.Scanning.dll`. Two generators built against different versions then rely on the compiler loading each package’s analyzers in a separate load context, which compilers running on .NET do. The Sources package avoids the question: there is no separate assembly to load. Specular’s own generator uses the library this way. Requirements for both packages: * The generator targets `netstandard2.0` and builds against `Microsoft.CodeAnalysis.CSharp` **5.0 or later**. The DLL package holds a build of the library for Roslyn 5.0, 5.3, 5.6, 5.9 and 5.12. * **Reference the package with `PrivateAssets="all"`.** It’s a build-time dependency of your generator, not something the projects that use your generator should reference. Without it, the DLL package warns with `SPECSCAN001`. ### `Specular.Scanning` (DLL) [Section titled “Specular.Scanning (DLL)”](#specularscanning-dll) 
```xml
<ItemGroup>
    <PackageReference Include="Microsoft.CodeAnalysis.CSharp" Version="5.0.0" PrivateAssets="all" />
    <PackageReference Include="Specular.Scanning" Version="x.y.z" PrivateAssets="all" />
</ItemGroup>
```
 The package depends on `System.Text.Json` and `System.Collections.Immutable` 9.0.21 or later, so you don’t reference them yourself; an older version pinned in your project fails restore with `NU1605`. When you pack the generator, the package adds `Specular.Scanning.dll` and its `System.Text.Json.dll` to every `analyzers/` folder your generator is packed into. If you reference a newer `System.Text.Json` than the bundled one, pack that `System.Text.Json.dll` beside your generator yourself; a file your project packs takes precedence. See [Packaging](#packaging-and-msbuild). ### `Specular.Scanning.Sources` (source-only) [Section titled “Specular.Scanning.Sources (source-only)”](#specularscanningsources-source-only) 
```xml
<ItemGroup>
    <PackageReference Include="Microsoft.CodeAnalysis.CSharp" Version="5.0.0" PrivateAssets="all" />
    <PackageReference Include="Specular.Scanning.Sources" Version="x.y.z" PrivateAssets="all" />
    <!-- The sources use System.Text.Json and immutable collections; reference them yourself. -->
    <PackageReference Include="System.Text.Json" Version="9.0.0" PrivateAssets="all" />
    <PackageReference Include="System.Collections.Immutable" Version="9.0.0" PrivateAssets="all" />
</ItemGroup>
```
 * The sources need **C# 14**. A `netstandard2.0` project defaults to C# 7.3, so the package sets `LangVersion` to 14 when your project doesn’t set it. If your project sets a version older than 14, the build fails with `SPECSCAN005` and tells you to raise it. The package never overrides a `LangVersion` you set. * The package depends on [Polyfill](https://github.com/SimonCropp/Polyfill), which is also source-only, and turns on its argument-exception back-ports (`PolyArgumentExceptions`) unless you set that property yourself. * The types are compiled as `internal` (the package defines `SPECULAR_SCANNING_SOURCES`), so they never become part of your generator’s API. * Your generator now depends on `System.Text.Json` at run time. Ship `System.Text.Json.dll` beside your generator, as you would any generator dependency. ## A complete generator [Section titled “A complete generator”](#a-complete-generator) The generator below finds every concrete class that implements `Plugins.IPlugin`, in the project and in everything it references, and generates a `PluginRegistry` that lists them. 
```csharp
using System.Collections.Immutable;
using System.Linq;
using System.Text;
using Microsoft.CodeAnalysis;
using Specular.Scanning;


[Generator(LanguageNames.CSharp)]
public sealed class PluginRegistryGenerator : IIncrementalGenerator
{
    // Unique to this generator. It names the cache file: obj/<configuration>/<tfm>/ctp/PluginRegistry.ctpjson.
    private const string ConsumerId = "PluginRegistry";


    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        // 1. Describe the scan. This runs on every compilation change, but a ScanRequest is equatable,
        //    so nothing downstream reruns while the request stays the same.
        var request = context.CompilationProvider.Select(static (compilation, _) =>
            compilation.GetTypeByMetadataName("Plugins.IPlugin") is { } plugin
                ? ScanRequest.Build(compilation, s => s
                    .FromAssemblies()
                    .GetTypes(f => f
                        .AssignableTo(plugin)
                        .KindOf(TypeKind.Class)
                        .NotInfoOf(TypeInfoFilter.Abstract, TypeInfoFilter.GenericType)))
                // An empty selection matches nothing.
                : ScanRequest.Build(compilation, static _ => { }));


        // 2. Run it. A referenced assembly is walked once, then served from memory or from the cache file
        //    until it changes.
        IncrementalValueProvider<ScanResult> result = context.Scan(ConsumerId, request);


        // 3. Keep only what the output needs, as an equatable value.
        var plugins = result.Select(static (scan, _) => new EquatableArray<string>(
            scan.Types
                .Where(static type => type.IsAccessible)
                .Select(static type => type.FullyQualifiedName)
                .ToImmutableArray()));


        context.RegisterSourceOutput(plugins, static (output, names) =>
        {
            var source = new StringBuilder()
                .AppendLine("namespace Plugins;")
                .AppendLine()
                .AppendLine("public static class PluginRegistry")
                .AppendLine("{")
                .AppendLine("    public static global::System.Type[] All { get; } = new global::System.Type[]")
                .AppendLine("    {");
            foreach (var name in names)
            {
                source.Append("        typeof(").Append(name).AppendLine("),");
            }


            source.AppendLine("    };").AppendLine("}");
            output.AddSource("PluginRegistry.g.cs", source.ToString());
        });
    }
}
```
 Points to notice: * `ScanRequest.Build(compilation, select)` runs your selection against a compilation and returns a `ScanRequest`: a read-only record that names assemblies and types by metadata name, not by symbol. It’s the value that flows through your pipeline and keys the cache. * `context.Scan(consumerId, request)` is an extension method on `IncrementalGeneratorInitializationContext`. It returns an `IncrementalValueProvider<ScanResult>`. It also adds the steps that read and write the cache file. * `ScanResult` is equatable, so you can `Select` from it directly. The step above reduces it to a list of type names, so the output step reruns only when that list changes. * The type-name trick only works for non-generic types, which the filter guarantees. For anything more involved, resolve the result back to symbols in the output step: see [Results](#results). ### Several requests [Section titled “Several requests”](#several-requests) If your generator needs more than one scan, pass all of them to **one** `Scan` call, as an `IncrementalValuesProvider<ScanRequest>`. You get one `ScanResult` per request, in request order, and a request listed twice is scanned once. 
```csharp
var requests = context.CompilationProvider.SelectMany(static (compilation, _) => ImmutableArray.Create(
    ScanRequest.Build(compilation, s => s.FromAssemblies().GetTypes(f => f.EndsWith("Handler"))),
    ScanRequest.Build(compilation, s => s.DependenciesFromAssembly("MyFramework"))));


IncrementalValuesProvider<ScanResult> results = context.Scan(ConsumerId, requests);
```
 When you know the scans up front, pass them as a tuple instead, and read each result by name. There are overloads for 2 to 8 requests; the results come back in the same positions, and the tuple compares by value, so the pipeline caches it: 
```csharp
var requests = context.CompilationProvider.Select(static (compilation, _) => (
    ScanRequest.Build(compilation, s => s.FromAssemblies().GetTypes(f => f.EndsWith("Handler"))),
    ScanRequest.Build(compilation, s => s.DependenciesFromAssembly("MyFramework"))));


IncrementalValueProvider<(ScanResult, ScanResult)> results = context.Scan(ConsumerId, requests);


context.RegisterSourceOutput(results, static (output, scans) =>
{
    var (handlers, dependents) = scans;
    // ...
});
```
 Tuple element names are compile-time only, so they don’t carry from the requests to the results: name the results where you read them, as above. If the requests come from different parts of your pipeline, pass the providers separately instead (2 to 8 of them). They’re combined into one scan, and the results come back in parameter order: 
```csharp
var handlers = context.CompilationProvider.Select(static (compilation, _) => ScanRequest.Build(compilation, BuildHandlerScan));
var plugins = context.CompilationProvider.Select(static (compilation, _) => ScanRequest.Build(compilation, BuildPluginScan));


IncrementalValueProvider<(ScanResult, ScanResult)> results = context.Scan(ConsumerId, handlers, plugins);
```
 Don’t call `Scan` twice with the same consumer id. Each call saves only the entries its own requests used, so two calls that share a file keep overwriting each other’s entries. ## The selector API [Section titled “The selector API”](#the-selector-api) The selectors mirror Specular’s runtime selectors (`IReflectionAssemblySelector`, `IReflectionTypeSelector` and `ITypeFilter`) as `IAssemblySymbolSelector`, `ITypeSymbolSelector` and `ITypeSymbolFilter`. If you know one, you know the other. The differences: * **`Type` becomes `ITypeSymbol`.** Get symbols from the compilation you were given, for example with `compilation.GetTypeByMetadataName("MyLib.IHandler")`. * **There are no generic `<T>` overloads.** `FromAssemblyOf<T>()` becomes `FromAssemblyOf(symbol)`. A generator can’t name the user’s types as type arguments. * **String overloads take metadata names.** Assemblies are named by `IAssemblySymbol.MetadataName` (`"MyLib"`). Types are named by their full metadata name: namespaces joined with `.`, nested types with `+`, and generic types with their arity (``"MyLib.IHandler`1"``, `"MyLib.Outer+Inner"`). * **Assemblies can be named directly.** `FromAssembly`, `NotFromAssembly` and `DependenciesFromAssembly` take an `IAssemblySymbol` or an assembly name. * **`GetTypes` returns nothing.** It makes the request a types scan. Without it the request is an assemblies scan. * **`KindOf` takes Roslyn’s `TypeKind`.** Its `Array`, `Class`, `Delegate`, `Enum`, `Interface` and `Struct` values are the same as Specular’s `TypeKindFilter`. `InfoOf` takes `Specular.Scanning.TypeInfoFilter`, which has the same members and values as Specular’s. * **`Where(CustomTypeFilter)`** adds a filter of your own. See [Custom filters](#custom-filters). ### Assembly selection [Section titled “Assembly selection”](#assembly-selection) | Specular (runtime) | Specular.Scanning | | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------- | | `EntryAssembly()` | `EntryAssembly()` | | `FromAssemblies()` | `FromAssemblies()` | | `FromAssemblyOf<T>()`, `FromAssemblyOf(Type)` | `FromAssemblyOf(ITypeSymbol)`, `FromAssembly(IAssemblySymbol)`, `FromAssembly(string)` | | `NotFromAssemblyOf<T>()`, `NotFromAssemblyOf(Type)` | `NotFromAssemblyOf(ITypeSymbol)`, `NotFromAssembly(IAssemblySymbol)`, `NotFromAssembly(string)` | | `DependenciesFromAssemblyOf<T>()`, `(Type)` | `DependenciesFromAssemblyOf(ITypeSymbol)`, `DependenciesFromAssembly(IAssemblySymbol)`, `(string)` | | `IncludeSystemAssemblies()` | `IncludeSystemAssemblies()` | | `GetTypes()`, `GetTypes(bool publicOnly)` | `GetTypes()`, `GetTypes(bool publicOnly)` | | `GetTypes(Action<ITypeFilter>)`, `(bool, Action<…>)` | `GetTypes(Action<ITypeSymbolFilter>)`, `GetTypes(bool, Action<ITypeSymbolFilter>)` | ### Type filters [Section titled “Type filters”](#type-filters) Every filter call adds a clause, and a type must match all of them. | Specular (runtime) | Specular.Scanning | | -------------------------------------------------------------- | ---------------------------------------------------------------------- | | `AssignableTo<T>()`, `AssignableTo(Type)` | `AssignableTo(ITypeSymbol)`, `AssignableTo(string metadataName)` | | `AssignableToAny(Type, params Type[])` | `AssignableToAny(ITypeSymbol, params ITypeSymbol[])` | | `NotAssignableTo<T>()`, `NotAssignableTo(Type)` | `NotAssignableTo(ITypeSymbol)`, `NotAssignableTo(string metadataName)` | | `NotAssignableToAny(Type, params Type[])` | `NotAssignableToAny(ITypeSymbol, params ITypeSymbol[])` | | `StartsWith`, `EndsWith`, `Contains` and their `Not…` forms | The same, with the same `(string, params string[])` signatures | | `InExactNamespaceOf<T>()`, `(Type, params Type[])` | `InExactNamespaceOf(ITypeSymbol, params ITypeSymbol[])` | | `InNamespaceOf<T>()`, `NotInNamespaceOf<T>()` and `Type` forms | `InNamespaceOf(…)`, `NotInNamespaceOf(…)` with `ITypeSymbol` arguments | | `InExactNamespaces`, `InNamespaces`, `NotInNamespaces` | The same, with the same `(string, params string[])` signatures | | `WithAttribute<T>()`, `(Type)`, `(string)` | `WithAttribute(ITypeSymbol)`, `WithAttribute(string)` | | `WithAnyAttribute(Type, …)`, `(string, …)` | `WithAnyAttribute(ITypeSymbol, …)`, `WithAnyAttribute(string, …)` | | `WithoutAttribute<T>()`, `(Type)`, `(string)` | `WithoutAttribute(ITypeSymbol)`, `WithoutAttribute(string)` | | `KindOf(TypeKindFilter, …)`, `NotKindOf(…)` | `KindOf(TypeKind, …)`, `NotKindOf(TypeKind, …)` | | `InfoOf(TypeInfoFilter, …)`, `NotInfoOf(…)` | `InfoOf(TypeInfoFilter, …)`, `NotInfoOf(…)` | | none | `Where(CustomTypeFilter)` | The rules match Specular’s own generator: * **Name filters** compare the type’s simple name (`type.Name`, without namespace or generic arity), case-sensitively. * **`InNamespaces` and `NotInNamespaces` compare by prefix**, so `InNamespaces("MyApp.Foo")` also matches `MyApp.FooBar`. Use `InExactNamespaces` for an exact match. * **Generics.** Pass the generic definition (``GetTypeByMetadataName("MyLib.IHandler`1")``, or the string ``"MyLib.IHandler`1"``) to match every closed form, through the type itself, its base types or its interfaces. Pass a constructed type, such as `IHandler<int>` built with `handler.Construct(compilation.GetSpecialType(SpecialType.System_Int32))`, to match only that closed type; variance applies as in C#, so `IVariant<object>` matches a type implementing `IVariant<string>`. Type arguments must be named types (nested, constructed, tuples and `int?` are fine) or arrays of them, so `IHandler<int[]>` and `IHandler<string[,]>` work too; pointers, type parameters and `dynamic` as arguments throw `ArgumentException`. The string overloads can’t express type arguments. * **`object` is never a match** for `AssignableTo`, as in Specular. * **Attributes** are read from the type itself, not inherited. `WithAttribute(symbol)` needs the exact attribute class. `WithAnyAttribute(symbol, …)` compares name and namespace, so a generic attribute definition matches every closed use of it. * **A type that can’t be found matches nothing.** An include clause whose types don’t resolve matches no type, so `AssignableTo("MyLib.IHandlr")` with a typo returns nothing rather than everything; an exclude clause ignores a type it can’t find. Every reference that didn’t resolve is listed in `ScanResult.UnresolvedTypes`, so your generator can report a diagnostic. A type named by string is looked up with `Compilation.GetTypeByMetadataName`, which also finds nothing when two referenced assemblies define the same name; a symbol overload records the type’s assembly, so it doesn’t have that problem. Prefer symbol overloads, and check for `null` when you look a symbol up, as the example does. A request with an unresolved type is never cached, so it recovers as soon as the type appears. * `WithAttribute(string)` and its relatives compare the full metadata name of each applied attribute’s class, without looking the name up. * Only named types can be selected as the type a filter names. Arrays, pointers, type parameters and error types throw `ArgumentException` there; an array is fine as a type argument of a closed generic. ### How assembly selections combine [Section titled “How assembly selections combine”](#how-assembly-selections-combine) Several specific selections are **alternatives**. `FromAssemblies()` is the starting point they narrow, and `NotFrom…` always excludes. All of it happens within the project’s [assembly scope](../reference/assembly-scope/): by default every assembly but the framework’s. A selection that names an assembly (`FromAssembly…`) reaches it even when it is out of scope, and `IncludeSystemAssemblies()` brings back what only the framework default leaves out. 1. Core assemblies (`mscorlib`, `netstandard`, `System`, `System.Core`, `System.Runtime`, `System.Private.CoreLib`) are skipped unless you call `IncludeSystemAssemblies()`, even when you name them. 2. An assembly named by any `NotFrom…` call is excluded, whatever else selects it. 3. If there’s at least one specific selection (`EntryAssembly`, `FromAssembly…` or `DependenciesFromAssembly…`), an assembly matches when **any** of them selects it. `FromAssemblies()` then adds nothing. 4. With no specific selection, every assembly that’s left matches. That includes the compilation’s own assembly. 5. An empty selection matches nothing. | Selection | Scans | | ------------------------------------------------- | ---------------------------------------------------------------------------------- | | `FromAssemblies()` | Every assembly in scope: the references and the compilation’s own | | `FromAssemblyOf(a)` | `a`’s assembly | | `FromAssemblyOf(a).FromAssemblyOf(b)` | `a`’s assembly **and** `b`’s assembly | | `FromAssemblies().FromAssemblyOf(a)` | Only `a`’s assembly | | `DependenciesFromAssemblyOf(t)` | Every assembly that directly references `t`’s assembly (not `t`’s assembly itself) | | `FromAssemblies().DependenciesFromAssemblyOf(t)` | The same: every assembly that references `t`’s assembly | | `FromAssemblyOf(a).DependenciesFromAssemblyOf(c)` | `a`’s assembly, plus every assembly that references `c`’s assembly | | `FromAssemblies().NotFromAssemblyOf(x)` | Every assembly except `x`’s | | `NotFromAssemblyOf(x)` | Every assembly except `x`’s | | `FromAssemblyOf(a).NotFromAssemblyOf(a)` | Nothing | | `IncludeSystemAssemblies()` | Every assembly, core and framework assemblies included | `DependenciesFromAssembly` with an assembly the compilation doesn’t reference selects nothing. It still counts as a specific selection, so it never widens the scan to everything. ### Selector rules [Section titled “Selector rules”](#selector-rules) * The selector is only valid inside the `ScanRequest.Build` callback. Calling it afterwards throws. * `GetTypes` can be called once per selection. * The same selection always builds an equal request with the same `CacheKey`. An assembly named twice is recorded once, and the `IAssemblySymbol`, type and name overloads of an assembly selection build the same request. For type filters the symbol and string overloads build different requests (see above), though they match the same types when both resolve. ### Custom filters [Section titled “Custom filters”](#custom-filters) Derive from `CustomTypeFilter` for a rule the built-in filters can’t express: 
```csharp
public sealed class HasParameterlessConstructor : CustomTypeFilter
{
    // Bump the version whenever IsMatch changes what it matches.
    public override string CacheKey => "has-parameterless-ctor/v1";


    public override bool IsMatch(Compilation compilation, INamedTypeSymbol type) =>
        type.InstanceConstructors.Any(static ctor => ctor.Parameters.IsEmpty && ctor.DeclaredAccessibility == Accessibility.Public);
}


var request = ScanRequest.Build(compilation, s => s
    .FromAssemblies()
    .GetTypes(f => f.AssignableTo(plugin).Where(new HasParameterlessConstructor())));
```
 The filter’s logic can’t be compared or saved, so its `CacheKey` stands in for it: * Two filters are equal when they’re the same class with the same `CacheKey`. The class name and the key are part of the request’s `CacheKey`, which names the cache entries. * **`CacheKey` must change whenever what the filter matches changes.** That includes any parameters the filter holds, and the filter’s own logic when you ship a new version of your generator. If it doesn’t change, a build keeps using the results it saved before, for as long as the referenced assembly stays the same. * `IsMatch` should depend only on `type` and the assemblies it comes from. Results for a referenced assembly are reused while that assembly is unchanged, even when the project’s own code changes. * Custom filters run after every built-in clause, so they only see types that already passed the rest. ## Results [Section titled “Results”](#results) A scan returns a `ScanResult`: | Member | What it holds | | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | | `Request` | The `ScanRequest` that produced it. | | `Assemblies` | `EquatableArray<ScannedAssembly>`: the assemblies that passed the assembly filter, ordered by name. | | `Types` | `EquatableArray<ScannedType>`: for a types scan, the matched types ordered by assembly and metadata name. Empty for an assemblies scan. | | `UnresolvedTypes` | `EquatableArray<TypeReference>`: each type the request’s filters named that couldn’t be resolved, in order of first appearance. | | `Resolve(Compilation)` | The same result as symbols, in a `ScanSymbols` (`Assemblies` and `Types` as immutable arrays). | `ScannedAssembly` has the assembly’s `Name` and `HasInaccessibleMatches`: whether any type matched in it can’t be referenced from the compilation. `ScannedType` describes a type by value, so results can be cached and compared: | Property | Meaning | | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `AssemblyName` | The containing assembly’s metadata name. | | `MetadataName` | The full metadata name, as `GetTypeByMetadataName` takes it (`MyLib.Outer+Inner`, ``MyLib.IHandler`1``). | | `FullyQualifiedName` | A `global::`-qualified C# name to emit (`global::MyLib.Outer.Inner`, `global::MyLib.IHandler<T>`). For `typeof` of an open generic, keep only the commas inside each `<…>` (`global::MyLib.IHandler<>`). | | `Kind` | The Roslyn `TypeKind`. | | `DeclaredAccessibility` | The declared accessibility. | | `IsAccessible` | Whether the compilation can reference the type. This takes into account the declared accessibility, the containing types and `InternalsVisibleTo`. | | `Arity` | The number of generic type parameters. | Scans also return types your generated code can’t name, such as `internal` types in another assembly. Check `IsAccessible` before you emit `typeof(...)` or a `new` expression. `ScanSymbols` holds symbols, so it isn’t equatable. Use `Resolve` inside an output step, not as a pipeline value. Entries that no longer resolve are skipped: 
```csharp
context.RegisterSourceOutput(result.Combine(context.CompilationProvider), static (output, input) =>
{
    var (result, compilation) = input;
    foreach (INamedTypeSymbol type in result.Resolve(compilation).Types)
    {
        // type.ToDisplayString(SymbolDisplayFormat.FullyQualifiedFormat), its members, its attributes, ...
    }
});
```
 Combining with `CompilationProvider` makes the output step run on every compilation change. Where you can, reduce the result to an equatable model first, as the complete example does. ## Running a scan directly [Section titled “Running a scan directly”](#running-a-scan-directly) Outside an incremental pipeline (an analyzer, a test, a one-off transform), run a request yourself: 
```csharp
var request = ScanRequest.Build(compilation, s => s.FromAssemblyOf(marker).GetTypes(publicOnly: true));


ScanSymbols symbols = Scanner.Run(compilation, request, cancellationToken);   // symbols
ScanResult result = Scanner.Scan(compilation, request, cancellationToken);    // the equatable result
```
 `Scanner.Run` and `Scanner.Scan` don’t use any cache. Every call walks every selected assembly. ## Caching [Section titled “Caching”](#caching) `context.Scan` caches the types each request matched in each **referenced** assembly. Nothing else needs to be set up in the generator. * **One file per consumer id**, at `$(IntermediateOutputPath)ctp/<ConsumerId>.ctpjson`, for example `obj/Debug/net10.0/ctp/PluginRegistry.ctpjson`. A build writes it and feeds it back to the next build as an additional file. * **Consumer ids** are ASCII letters, digits, `.`, `_` and `-`, and can’t be empty. Anything else throws `ArgumentException`. Pick an id unique to your generator. File names are matched ignoring case, and `SpecularProvider` is Specular’s own. Generators never read each other’s files. * **One `Scan` call per consumer id.** See [Several requests](#several-requests). * **Entries stay valid while the assembly’s MVID is unchanged.** The module version id changes whenever the assembly is rebuilt with different content. Entries are kept per request (its `CacheKey`) and per assembly. * **Only references with a readable MVID are cached on disk.** That means `PortableExecutableReference`s: package and framework references, and project references in a command-line build. In the IDE, project references arrive as compilation references with no MVID, so they’re always rescanned rather than read from the file. * **The compilation’s own assembly is never cached.** It changes with every edit, so it’s walked on every run. * **While you type, results are reused in memory.** A referenced assembly’s results are remembered for as long as the compiler keeps the same reference object, so an edit in the project doesn’t rescan its references. * **Only builds save the file.** It’s written from an implementation-only output, which the IDE doesn’t run. It’s written only when its content changed, so an unchanged cache doesn’t touch the file’s timestamp or make the project out of date. * **Each save keeps only what the run used.** Entries for removed references or requests drop out. * **A missing, corrupt or outdated file is ignored and rebuilt.** The cache never fails a build, and nothing is written outside MSBuild. The file format is described in [Scan cache file](../../architecture/scan-cache-file/). ### Storing your own data [Section titled “Storing your own data”](#storing-your-own-data) A generator often derives something else from each referenced assembly, such as a manifest read from its attributes. `ScanCache` stores such values per assembly, under the same MVID rules, in a consumer’s cache file. Values are serialized with a `JsonTypeInfo<T>` you supply from a source-generated `JsonSerializerContext` (the DLL package brings `System.Text.Json` and its source generator; with the Sources package you reference it yourself): 
```csharp
public sealed class PluginManifest
{
    public string Name { get; set; } = "";
    public string[] Capabilities { get; set; } = [];
}


[JsonSerializable(typeof(PluginManifest))]
internal sealed partial class ManifestJsonContext : JsonSerializerContext { }
```
 Use the store through the `Scan` overload that takes a transform. The transform runs in the same pipeline step as the scans, gets the run’s cache, and whatever it reads or writes is saved in the same file as the scan results, under the same consumer id: 
```csharp
private const int ManifestVersion = 1;


IncrementalValueProvider<PluginModel> model = context.Scan(ConsumerId, requests, static scan =>
{
    var manifests = ImmutableArray.CreateBuilder<PluginManifest>();
    foreach (var assembly in scan.Compilation.SourceModule.ReferencedAssemblySymbols)
    {
        if (!scan.Cache.TryGet("manifest", assembly, ManifestJsonContext.Default.PluginManifest, ManifestVersion, out var manifest))
        {
            manifest = ReadManifest(assembly);
            scan.Cache.Set("manifest", assembly, manifest, ManifestJsonContext.Default.PluginManifest, ManifestVersion);
        }


        manifests.Add(manifest);
    }


    // The output is a pipeline value: make it equatable by value, and never keep symbols, the compilation or `scan` in it.
    return new PluginModel(scan.Results, manifests.ToImmutable());
});
```
 `scan` is a `ScanContext` with the `Compilation`, the `Results` in request order, the run’s `Cache` and the `CancellationToken`. It’s only valid while the transform runs, and the cache is saved for you: don’t call `Save`. Store values are also remembered in memory while a referenced assembly is unchanged, as scan results are, so typing in the IDE doesn’t recompute them. A generator that doesn’t scan can still use the store by loading and saving a `ScanCache` itself in an implementation output: `ScanCache.Load(consumerId, compilation, additionalFiles)`, then `TryGet`/`Set`, then `Save(options.GlobalOptions)`. Don’t combine that with `context.Scan` under the same consumer id: each writes the whole file, so they would drop each other’s entries. * `TryGet` hits only when the assembly’s MVID matches **and** the value was stored with the same data version. Bump your data version when the shape or meaning of the value changes. * `Set` does nothing for an assembly that can’t be cached: the compilation’s own, or a reference without an MVID. * `Save` writes the entries read or written in this run to `$(IntermediateOutputPath)ctp/<ConsumerId>.ctpjson`, and only when the content changed. It does nothing outside MSBuild and never throws on IO errors. * `ScanCache` is safe to use from several threads within one run. It isn’t equatable, so don’t pass it through the pipeline. ## Packaging and MSBuild [Section titled “Packaging and MSBuild”](#packaging-and-msbuild) The cache only works if the projects that use your generator feed the cache file back to the compiler. Both packages take care of this when you pack your generator: there’s nothing to add to your project beyond the `PackageReference`. ### What happens when you pack [Section titled “What happens when you pack”](#what-happens-when-you-pack) The package imports a pack helper into your generator’s project. When the project is packed: 1. **DLL package only:** `Specular.Scanning.dll` (and `System.Text.Json.dll`) is added to every `analyzers/` folder that your generator packs a `.dll` into. A folder for a Roslyn version, such as `analyzers/dotnet/roslyn5.9/cs`, gets the newest build of the library for that version or older. A folder without one, such as `analyzers/dotnet/cs`, gets the Roslyn 5.0 build. Files you already pack into a folder are left alone. 2. **The cache wiring:** `build/` and `buildTransitive/` get `Specular.Scanning.Cache.targets` and a `<PackageId>.targets` that imports it. If you already pack your own `<PackageId>.targets`, a `<PackageId>.props` is used instead. The import is guarded, so a project that uses several such generators imports it once. The wiring, in each project that uses your generator: * adds every existing `$(IntermediateOutputPath)ctp/*.ctpjson` to `AdditionalFiles` just before `CoreCompile` (each generator picks out its own file), once per file even when Specular adds its own file too; * deletes the files on `Clean`; * makes `IntermediateOutputPath` and `ProjectDir` visible to generators, which write the cache there. A project that uses the generator can set `SpecularScanningCache` to `false` to stop feeding the files back. Generators then rescan on every build, and `Clean` still deletes the files. ### Properties [Section titled “Properties”](#properties) Set these in your generator’s project file. | Property | Default | Effect | | ------------------------------------ | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | | `SpecularScanningPack` | `true` | `false` adds nothing to the package. | | `SpecularScanningBundleLibrary` | `true` | `false` leaves `Specular.Scanning.dll` out of the `analyzers/` folders; the generator then has to ship it. DLL package only. | | `SpecularScanningPackCacheTargets` | `true` | `false` leaves the cache wiring out of the package. For a project that uses the generator through a `ProjectReference`. | The helper finds your `analyzers/` folders from what the project packs: `None` and `Content` items with `Pack="true"` and a `PackagePath`, and `TfmSpecificPackageFile` items. <ItemGroup>
    <ProjectReference Include="../MyGenerator/MyGenerator.csproj" OutputItemType="Analyzer" ReferenceOutputAssembly="false" />
    <!-- Only for the cache wiring. -->
    <PackageReference Include="Specular.Scanning" Version="x.y.z" PrivateAssets="all" IncludeAssets="build" />

 * With the DLL package, the generator’s project returns `Specular.Scanning.dll` and its `System.Text.Json.dll` from `GetTargetPath`, so the referencing project passes both to the compiler beside the generator. * A test project that runs the generator in-process (with `CSharpGeneratorDriver`) gets `Specular.Scanning.dll` copied to its output but not listed in its `.deps.json`, so loading the generator fails with `FileNotFoundException`. ```xml
<ItemGroup>
    <ProjectReference Include="../Specular.Scanning/Specular.Scanning.csproj" PrivateAssets="all" />
</ItemGroup>

    <SpecularScanningLibraryAssembly>$(MSBuildThisFileDirectory)../Specular.Scanning.supports/bin/roslyn5.0/$(Configuration)/netstandard2.0/Specular.Scanning.dll</SpecularScanningLibraryAssembly>

# Reference [Section titled “Reference”](#reference) This section documents Specular’s **public API surface**: the interface your code calls, the attributes that control what gets scanned, and the fluent filters that shape selector expressions. Everything here is a stable contract — the runtime package (`Specular`) is intentionally tiny, and almost all of the work happens in the source generator. ## Pages Stable [Section titled “Pages ”Stable](#pages) * [ISpecularProvider](./ispecular-provider/) — the generated entry point, accessed via the static `SpecularProvider.Instance` singleton. # Assembly scope

> Which assemblies Specular's scans look in by default, and the SpecularExcludeAssemblies and SpecularIncludeAssemblies properties that change them.

# Assembly scope [Section titled “Assembly scope”](#assembly-scope) A selector that does not name its assemblies (`FromAssemblies()`, `NotFromAssemblyOf<T>()`, `DependenciesFromAssemblyOf<T>()`) looks in the project’s **assembly scope**. By default that is every assembly the project references, plus its own, **except the framework**: * assemblies signed with one of Microsoft’s framework keys (the BCL, ASP.NET Core, `Microsoft.Extensions.*`, and so on), and * assemblies named `netstandard`, `mscorlib`, `System`, `System.*`, `Microsoft.*` or `WindowsBase`, for builds of them without those keys. The project’s own assembly is always in scope. ## Changing it [Section titled “Changing it”](#changing-it) Set two properties in the project file. Each takes patterns separated by `;` or `,`; a pattern matches the whole assembly name, ignores case, and can use `*` (any run of characters) and `?` (one character): 
```xml
<PropertyGroup>
    <!-- Leave these out of broad scans. -->
    <SpecularExcludeAssemblies>$(SpecularExcludeAssemblies);Contoso.Legacy.*;Contoso.Tests</SpecularExcludeAssemblies>


    <!-- Bring these in, whatever excludes them, the framework default included. -->
    <SpecularIncludeAssemblies>$(SpecularIncludeAssemblies);Microsoft.Extensions.Logging</SpecularIncludeAssemblies>
</PropertyGroup>
```
 **An include always wins.** An assembly that matches any `SpecularIncludeAssemblies` pattern is in scope, even if an exclude pattern or the framework default would leave it out. `<SpecularIncludeAssemblies>*</SpecularIncludeAssemblies>` scans everything. These are properties rather than items because MSBuild expands `*` and `?` in an item’s `Include` as a file glob: an item pattern would quietly disappear, or turn into the names of files in your project folder. | Pattern | Matches | | ----------------- | -------------------------------------------------------- | | `Contoso` | `Contoso` only | | `Contoso.*` | `Contoso.Billing`, `Contoso.Billing.Data`, not `Contoso` | | `Contoso*` | `Contoso`, `Contoso.Billing`, `ContosoTools` | | `*.Tests` | `Contoso.Tests`, `Fabrikam.Tests` | | `Contoso.?illing` | `Contoso.Billing`, `Contoso.Filling` | ## What a selector can still reach [Section titled “What a selector can still reach”](#what-a-selector-can-still-reach) The scope decides what a selector that does not name an assembly looks in. A selector can still reach outside it for that one call: * `FromAssemblyOf<T>()` and `FromAssemblies(typeof(T))` scan `T`’s assembly even when it is out of scope. * `IncludeSystemAssemblies()` brings back the assemblies only the framework default leaves out. It does not bring back the ones your `SpecularExcludeAssemblies` patterns exclude. `[assembly: ExcludeFromSpecular]` (see [ExcludeFromSpecularAttribute](./exclude-from-specular/)) still takes precedence over everything: no selector scans such an assembly. An assembly out of scope also contributes none of the scans it declares itself: its `GetTypes` and `Scan` calls are not resolved again in your project. ## Migrating from `ExcludeAssemblyFromCTP` [Section titled “Migrating from ExcludeAssemblyFromCTP”](#migrating-from-excludeassemblyfromctp) The `ExcludeAssemblyFromCTP` property is no longer read. It matched names by prefix, so `System` also left out `Systems.Billing`; the framework default now covers what its default value did. Move any entries you added to it into `SpecularExcludeAssemblies`, adding `*` where you relied on the prefix: 
```xml
<!-- Before -->
<ExcludeAssemblyFromCTP>$(ExcludeAssemblyFromCTP);Contoso.Legacy</ExcludeAssemblyFromCTP>


<!-- After -->
<SpecularExcludeAssemblies>$(SpecularExcludeAssemblies);Contoso.Legacy*</SpecularExcludeAssemblies>
```
 ## For generator authors [Section titled “For generator authors”](#for-generator-authors) The scope lives in `Specular.Scanning`, so a generator built on it gets the same default. `context.Scan(consumerId, ...)` reads the project’s patterns from the MSBuild properties `<consumerId>ExcludeAssemblies` and `<consumerId>IncludeAssemblies`, separated by `;` or `,`. Make them visible to the compiler and set them from whatever your package’s users write. Specular’s own, for the consumer id `SpecularProvider`: 
```xml
<!-- build/YourGenerator.props -->
<ItemGroup>
    <CompilerVisibleProperty Include="SpecularProviderExcludeAssemblies" />
    <CompilerVisibleProperty Include="SpecularProviderIncludeAssemblies" />
</ItemGroup>


<!-- build/YourGenerator.targets: in a target, so values set by later imports (Directory.Build.targets) are seen -->
<Target Name="_SpecularAssemblyScope" BeforeTargets="GenerateMSBuildEditorConfigFileShouldRun">
    <PropertyGroup>
        <SpecularProviderExcludeAssemblies>$(SpecularExcludeAssemblies)</SpecularProviderExcludeAssemblies>
        <SpecularProviderIncludeAssemblies>$(SpecularIncludeAssemblies)</SpecularProviderIncludeAssemblies>
    </PropertyGroup>
</Target>
```
 `Scanner.Scan(compilation, request)` applies the framework default; pass a `ScanAssemblyScope` to choose another (`ScanAssemblyScope.Everything`, `ScanAssemblyScope.FromOptions(globalOptions, consumerId)`, or one built from your own patterns).

# ExcludeFromSpecularAttribute

> Opt an assembly out of all Specular scan results at compile time.

# ExcludeFromSpecularAttribute [Section titled “ExcludeFromSpecularAttribute”](#excludefromspecularattribute) 
```csharp
[AttributeUsage(AttributeTargets.Assembly)]
public class ExcludeFromSpecularAttribute : Attribute
```
 `ExcludeFromSpecularAttribute` is an **assembly-level** attribute that tells the Specular generator to exclude the entire assembly from compiled type provider resolution. An excluded assembly will not contribute types to any `GetAssemblies`, `GetTypes`, or `Scan` call in other assemblies. > **Note:** The excluded assembly itself still has access to the compiled type provider — it can call `ISpecularProvider` methods normally. Only its own types are hidden from resolution in *other* assemblies that scan it. ## Usage [Section titled “Usage”](#usage) Place the attribute in any file within the assembly you want to exclude, using the `[assembly:]` target: 
```csharp
[assembly: ExcludeFromSpecular]
```
 A common convention is to put assembly-level attributes in an `AssemblyInfo.cs` file or directly in the project’s top-level `Program.cs`. ## When to use it [Section titled “When to use it”](#when-to-use-it) * **Test assemblies** — prevent test fixture types, fakes, and stubs from appearing in production DI scans when the test project is referenced. * **Internal implementation assemblies** — a helper assembly that should never be scanned by consuming projects. * **Third-party or generated assemblies** — assemblies you reference but do not control, where you want to prevent their types from appearing in a broad `FromAssemblies()` scan. ## Compile-time exclusion [Section titled “Compile-time exclusion”](#compile-time-exclusion) This is a build-time decision. The Roslyn generator reads `[ExcludeFromSpecular]` from the assembly metadata during the build. The exclusion is baked into the generated provider — there is no runtime check and no performance cost. ## Interaction with other attributes [Section titled “Interaction with other attributes”](#interaction-with-other-attributes) `[ExcludeFromSpecular]` applies at the assembly level and takes precedence over everything else. Types in the excluded assembly will not appear in scan results even if those types carry `[ServiceRegistration]` or are otherwise matched by a fluent selector. ## See also [Section titled “See also”](#see-also) * [ISpecularProvider](./ispecular-provider) — the entry point for scanning operations * [Type Filters](./type-filters) — per-selector filtering, including `NotFromAssemblyOf<T>()` * [ServiceRegistrationAttribute](./service-registration) — attribute-driven type registration

# ISpecularProvider

> The generated provider interface — entry point for all compile-time scanning operations.

# ISpecularProvider [Section titled “ISpecularProvider”](#ispecularprovider) `ISpecularProvider` is the primary entry point for all compile-time scanning operations in Specular. At build time, the Roslyn source generator emits a concrete `SpecularProvider` implementation of this interface into your assembly. You access it through the generated static `SpecularProvider.Instance` property — no manual instantiation, no reflection. ## Accessing the Provider [Section titled “Accessing the Provider”](#accessing-the-provider) ### `SpecularProvider.Instance` [Section titled “SpecularProvider.Instance”](#specularproviderinstance) 
```csharp
public static ISpecularProvider Instance { get; }
```
 The source generator emits a concrete `SpecularProvider` class into your assembly and exposes it through the static `Instance` property. This is the entry point for all scanning — access it directly, with no reflection or `Activator.CreateInstance` involved: 
```csharp
ISpecularProvider provider = SpecularProvider.Instance;
```
 `SpecularProvider` is `internal` to the assembly the generator runs in, so `Instance` is available anywhere in that same assembly. Hold the returned `ISpecularProvider` in a field or local, or call `GetAssemblies`, `GetTypes`, and `Scan` on it inline. ### `GetArgumentExpressionHash(string)` [Section titled “GetArgumentExpressionHash(string)”](#getargumentexpressionhashstring) 
```csharp
[EditorBrowsable(EditorBrowsableState.Never)]
static string GetArgumentExpressionHash(string argumentExpression);
```
 Converts a selector expression string into a stable, compact key. Whitespace (spaces, tabs, newlines) is stripped before hashing so that formatting changes do not invalidate the cache. The resulting hash is an MD5-based Base64 string. This method is marked `[EditorBrowsable(Never)]` — it is called by generated code, not by application code. **Why it matters:** The generator keys every generated scan result to the *text* of the selector lambda at its call site. When the lambda changes (e.g. you add `.AssignableTo<INewService>()`), the hash changes, and the generator produces new output. Call sites that share the same expression text share the same generated result. ## Instance Methods [Section titled “Instance Methods”](#instance-methods) All three scanning methods share the same hidden caller-info parameters: | Parameter | Attribute | Purpose | | -------------------- | ---------------------------- | ----------------------------- | | `lineNumber` | `[CallerLineNumber]` | Line number of the call site | | `filePath` | `[CallerFilePath]` | File path of the call site | | `argumentExpression` | `[CallerArgumentExpression]` | Text of the selector argument | The compiler fills these in automatically. **Do not pass them explicitly.** The generator uses all three together to locate the exact call site and associate it with the generated output. ### `GetAssemblies` [Section titled “GetAssemblies”](#getassemblies) 
```csharp
IEnumerable<Assembly> GetAssemblies(
    Action<IReflectionAssemblySelector> action,
    [CallerLineNumber] int lineNumber = 0,
    [CallerFilePath] string filePath = "",
    [CallerArgumentExpression(nameof(action))] string argumentExpression = ""
);
```
 Returns the set of `Assembly` objects that match the selector. The selector is expressed as an `Action<IReflectionAssemblySelector>`; the generator resolves the full list at build time. At runtime the generated implementation returns a pre-built collection — no reflection occurs. **Example:** 
```csharp
IEnumerable<Assembly> assemblies = provider.GetAssemblies(
    s => s.FromAssemblyOf<MyApp>()
);
```
 ### `GetTypes` [Section titled “GetTypes”](#gettypes) 
```csharp
IEnumerable<Type> GetTypes(
    Func<IReflectionTypeSelector, IEnumerable<Type>> selector,
    [CallerLineNumber] int lineNumber = 0,
    [CallerFilePath] string filePath = "",
    [CallerArgumentExpression(nameof(selector))] string argumentExpression = ""
);
```
 Returns the set of `Type` objects that match the selector. The selector is a `Func` that receives an `IReflectionTypeSelector` and returns a filtered `IEnumerable<Type>`. The generator evaluates the selector expression at build time. **Example:** 
```csharp
IEnumerable<Type> types = provider.GetTypes(
    s => s.FromAssemblyOf<MyApp>()
          .GetTypes(f => f.AssignableTo<IMyService>())
);
```
 ### `Scan` [Section titled “Scan”](#scan) 
```csharp
IServiceCollection Scan(
    IServiceCollection services,
    Action<IServiceDescriptorAssemblySelector> selector,
    [CallerLineNumber] int lineNumber = 0,
    [CallerFilePath] string filePath = "",
    [CallerArgumentExpression(nameof(selector))] string argumentExpression = ""
);
```
 Adds `ServiceDescriptor` entries to the supplied `IServiceCollection` based on the selector. Returns the same `IServiceCollection` so calls can be chained. The full list of registrations is resolved at build time; the generated implementation performs no reflection at runtime. **Example:** 
```csharp
services = provider.Scan(
    services,
    s => s.FromAssemblyOf<MyApp>()
          .AddClasses(c => c.AssignableTo<IMyService>())
          .AsImplementedInterfaces()
          .WithScopedLifetime()
);
```
 ## Why the selector expression text matters [Section titled “Why the selector expression text matters”](#why-the-selector-expression-text-matters) Because the generator captures the *text* of each selector argument via `[CallerArgumentExpression]`, the text is the identity of a call site. Two calls with identical expression text (after whitespace normalisation) share a single generated code path. A call site whose selector text changes between builds produces new generated output on the next build. This is why you should avoid dynamic string construction or code-generated selectors — the generator cannot evaluate them. ## See also [Section titled “See also”](#see-also) * [Type Filters](./type-filters) — the fluent API used inside selectors * [ServiceRegistrationAttribute](./service-registration) — attribute-driven registration alternative * [ExcludeFromSpecularAttribute](./exclude-from-specular) — opt an assembly out of scanning

# KeyedServiceRegistrationAttribute

> Mark classes for automatic keyed DI registration using compile-time scanning.

# KeyedServiceRegistrationAttribute [Section titled “KeyedServiceRegistrationAttribute”](#keyedserviceregistrationattribute) `KeyedServiceRegistrationAttribute` is the keyed-service counterpart to [`ServiceRegistrationAttribute`](./service-registration) — it behaves the same way, except every registration it produces is a [keyed service](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/dependency-injection?view=aspnetcore-10.0#keyed-services) (`ServiceDescriptor.KeyedSingleton`, `KeyedScoped`, `KeyedTransient`) resolved with `IServiceProvider.GetKeyedService`/`GetRequiredKeyedService`. Like `ServiceRegistrationAttribute`, the Specular generator reads the attribute at build time; no runtime reflection occurs. ## `[KeyedServiceRegistration]` [Section titled “\[KeyedServiceRegistration\]”](#keyedserviceregistration) 
```csharp
[AttributeUsage(AttributeTargets.Class, AllowMultiple = true)]
public sealed class KeyedServiceRegistrationAttribute : KeyedServiceRegistrationBaseAttribute
```
 Applied to a class, it instructs the generator to register the class under the given key. If no explicit service types are given, the type is registered — under that same key — against itself and every interface it implements. **Constructor:** 
```csharp
KeyedServiceRegistrationAttribute(object? key, ServiceLifetime lifetime, params Type[] serviceTypes)
```
 **Properties:** | Property | Type | Description | | -------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------- | | `Key` | `object?` | The service key. Must be a compile-time constant (string, number, bool, char, enum, `Type`, or `null`). | | `ServiceTypes` | `ImmutableArray<Type>` | The service types to register against. Empty means register against all implemented interfaces (plus self). | | `Lifetime` | `ServiceLifetime` | The DI lifetime. Always required. | `AllowMultiple = true` means a single class can carry multiple `[KeyedServiceRegistration]` attributes — for different keys, different service types, or different lifetimes. Two registrations are only considered duplicates (and raise a diagnostic) when both the **service type and the key** match. The same service type may be registered any number of times under distinct keys: 
```csharp
[KeyedServiceRegistration("primary", ServiceLifetime.Singleton, typeof(ICache))]
[KeyedServiceRegistration("fallback", ServiceLifetime.Singleton, typeof(ICache))]
public class RedisCache : ICache { }
```
 ## Generic overloads [Section titled “Generic overloads”](#generic-overloads) The generic variants provide a concise way to specify one to eight explicit service types without passing `typeof(...)` arguments. ### `KeyedServiceRegistrationAttribute<TService>` [Section titled “KeyedServiceRegistrationAttribute\<TService>”](#keyedserviceregistrationattributetservice) 
```csharp
[KeyedServiceRegistration<IMyService>("my-key", ServiceLifetime.Scoped)]
public class MyService : IMyService { }
```
 Registers `MyService` as `IMyService` under `"my-key"`. ### `KeyedServiceRegistrationAttribute<TService1, TService2>` through `<..., TService8>` [Section titled “KeyedServiceRegistrationAttribute\<TService1, TService2> through <..., TService8>”](#keyedserviceregistrationattributetservice1-tservice2-through--tservice8) Registers against up to eight explicit service types, all under the same key. Every generic variant requires both a `key` and a `ServiceLifetime` constructor argument — neither has a default. ## Interaction with `[RegistrationLifetime]` [Section titled “Interaction with \[RegistrationLifetime\]”](#interaction-with-registrationlifetime) [`RegistrationLifetimeAttribute`](./service-registration#registrationlifetime) can still override the resolved lifetime for an individual service type, keyed or not. Priority order (highest first): 1. `[RegistrationLifetime]` on the specific service type being registered. 2. The lifetime declared on `[KeyedServiceRegistration]` itself. 3. `[RegistrationLifetime]` on the decorated class. 4. `ServiceLifetime.Singleton`. 
```csharp
[RegistrationLifetime(ServiceLifetime.Scoped)]
public interface IService { }


// Registered as itself (Singleton, from the attribute) but as IService (Scoped, from the override)
[KeyedServiceRegistration("service-key", ServiceLifetime.Singleton, typeof(IService))]
public class Service : IService { }
```
 ## `AddSpecularServiceRegistrations` [Section titled “AddSpecularServiceRegistrations”](#addspecularserviceregistrations) `AddSpecularServiceRegistrations` (see [ServiceRegistrationAttribute](./service-registration#addspecularserviceregistrations)) scans for every `[ServiceRegistration]` **and** `[KeyedServiceRegistration]` variant in one pass — no separate call is needed for keyed types. 
```csharp
builder.Services.AddSpecularServiceRegistrations(SpecularProvider.Instance);
```
 ## Resolving keyed services [Section titled “Resolving keyed services”](#resolving-keyed-services) Registrations produced by `[KeyedServiceRegistration]` are resolved the normal keyed-DI way: 
```csharp
public class Consumer([FromKeyedServices("primary")] ICache cache) { }


// or
var cache = serviceProvider.GetRequiredKeyedService<ICache>("primary");
```
 ## Notes [Section titled “Notes”](#notes) * Registration is a **compile-time** operation. The generator discovers `[KeyedServiceRegistration]`-decorated types during the build, not at application startup. * Abstract classes and static classes are implicitly excluded. * A keyed registration and a non-keyed `[ServiceRegistration]` for the same service type on the same class coexist without conflict — keyed and non-keyed services occupy independent slots in the container. ## See also [Section titled “See also”](#see-also) * [ServiceRegistrationAttribute](./service-registration) — the non-keyed counterpart to this attribute * [ISpecularProvider](./ispecular-provider) — the provider that backs `AddSpecularServiceRegistrations` * [Type Filters](./type-filters) — the fluent alternative to attribute-based registration

# ServiceRegistrationAttribute

> Mark classes for automatic DI registration using compile-time scanning.

# ServiceRegistrationAttribute [Section titled “ServiceRegistrationAttribute”](#serviceregistrationattribute) `ServiceRegistrationAttribute` is a declarative way to mark a class for DI registration without writing an explicit fluent selector. The Specular generator reads the attribute at build time and includes the type in the generated provider; no runtime reflection occurs. ## `[ServiceRegistration]` [Section titled “\[ServiceRegistration\]”](#serviceregistration) 
```csharp
[AttributeUsage(AttributeTargets.Class, AllowMultiple = true)]
public class ServiceRegistrationAttribute : Attribute
```
 Applied to a class, it instructs the generator to register the class in the DI container. The lifetime is always required; if no explicit service types are given, the type is registered against every interface it implements (plus itself). **Constructors:** 
```csharp
// Register against explicit service types with a required lifetime
ServiceRegistrationAttribute(ServiceLifetime lifetime, params Type[] serviceTypes)
```
 **Properties:** | Property | Type | Description | | -------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------- | | `ServiceTypes` | `ImmutableArray<Type>` | The service types to register against. Empty means register against all implemented interfaces (plus self). | | `Lifetime` | `ServiceLifetime` | The DI lifetime. Always required. | `AllowMultiple = true` means a single class can carry multiple `[ServiceRegistration]` attributes to be registered against different service types or with different lifetimes simultaneously. The generic and non-generic forms can be mixed freely on the same class. When a class carries more than one attribute: * The class itself is registered once, using the lifetime of the first attribute (in declaration order). * Each service type is registered with the lifetime of the attribute that names it, and resolves to that single registration of the class. * A service type named by more than one attribute (whether generic or not) reports `RSGD0005` — a class cannot register the same service type twice. ## Generic overloads [Section titled “Generic overloads”](#generic-overloads) The generic variants provide a concise way to specify one to eight explicit service types without passing `typeof(...)` arguments. ### `ServiceRegistrationAttribute<TService>` [Section titled “ServiceRegistrationAttribute\<TService>”](#serviceregistrationattributetservice) 
```csharp
[ServiceRegistration<IMyService>(ServiceLifetime.Scoped)]
public class MyService : IMyService { }
```
 Registers `MyService` as `IMyService` with the given lifetime. ### `ServiceRegistrationAttribute<TService1, TService2>` [Section titled “ServiceRegistrationAttribute\<TService1, TService2>”](#serviceregistrationattributetservice1-tservice2) 
```csharp
[ServiceRegistration<IMyService, IAlternate>(ServiceLifetime.Scoped)]
public class MyService : IMyService, IAlternate { }
```
 Registers against two service types. ### `ServiceRegistrationAttribute<TService1, TService2, TService3>` through `<..., TService8>` [Section titled “ServiceRegistrationAttribute\<TService1, TService2, TService3> through <..., TService8>”](#serviceregistrationattributetservice1-tservice2-tservice3-through--tservice8) Registers against up to eight explicit service types. Every generic variant requires a `ServiceLifetime` constructor argument — there is no default. ## `[RegistrationLifetime]` [Section titled “\[RegistrationLifetime\]”](#registrationlifetime) 
```csharp
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Interface)]
public class RegistrationLifetimeAttribute : Attribute
```
 Overrides the DI lifetime for a type independently of `[ServiceRegistration]`. Useful when you want to set a single lifetime on a base class or interface and have it apply across all registrations of that type. 
```csharp
public RegistrationLifetimeAttribute(ServiceLifetime lifetime)
```
 | Property | Type | Description | | ---------- | ----------------- | ------------------------ | | `Lifetime` | `ServiceLifetime` | The overriding lifetime. | ## `AddSpecularServiceRegistrations` [Section titled “AddSpecularServiceRegistrations”](#addspecularserviceregistrations) 
```csharp
public static IServiceCollection AddSpecularServiceRegistrations(
    this IServiceCollection services,
    ISpecularProvider provider

```
 Extension method on `IServiceCollection` that uses `provider.Scan()` to find all classes decorated with any `[ServiceRegistration]` variant and adds them to the container. The scan itself is resolved at build time; this call at startup simply replays the pre-built registrations. **Usage:** 
```csharp

```
 ## Combined example [Section titled “Combined example”](#combined-example) 
```csharp
// Scoped service registered as IMyService — lifetime from [ServiceRegistration] itself
[ServiceRegistration<IMyService>(ServiceLifetime.Scoped)]
public class MyService : IMyService { }


// Class carrying a separate lifetime override via [RegistrationLifetime]
[ServiceRegistration(ServiceLifetime.Singleton)]
[RegistrationLifetime(ServiceLifetime.Scoped)]
public class AnotherService : IAnotherService { }


// Multiple registrations on one class
[ServiceRegistration<IMyService>(ServiceLifetime.Singleton)]
[ServiceRegistration<IAlternate>(ServiceLifetime.Transient)]

```
 
```csharp

```
 ## Notes [Section titled “Notes”](#notes) * Registration is a **compile-time** operation. The generator discovers `[ServiceRegistration]`-decorated types during the build, not at application startup. * Abstract classes and static classes are implicitly excluded — `AddClasses()` skips them by default. * If `ServiceTypes` is empty (i.e. the attribute is applied with no explicit type arguments), the class is registered against itself and every interface it implements. * Open generic classes are registered by their type definitions, so the non-generic form is the one to use for them: `[ServiceRegistration(ServiceLifetime.Scoped, typeof(IRepository<>))]` on `Repository<T>`. The generic attributes cannot name an open generic service type (attribute type arguments cannot use type parameters). ## See also [Section titled “See also”](#see-also) * [ISpecularProvider](./ispecular-provider) — the provider that backs `AddSpecularServiceRegistrations` * [KeyedServiceRegistrationAttribute](./keyed-service-registration) — the keyed-service counterpart to this attribute * [Type Filters](./type-filters) — the fluent alternative to attribute-based registration * [ExcludeFromSpecularAttribute](./exclude-from-specular) — opt an assembly out of all scanning

# Type Filters

> The fluent selector API for filtering types by class, interface, namespace, attribute, and assignability.

# Type Filters [Section titled “Type Filters”](#type-filters) Specular provides a fluent selector API for describing which assemblies and types the generator should include in a scan. There are two parallel selector hierarchies — one for reflection-based results (`GetAssemblies` / `GetTypes`) and one for DI registration (`Scan`). Both share the same `ITypeFilter` interface for per-type predicates. ## Assembly Selectors [Section titled “Assembly Selectors”](#assembly-selectors) ### `IReflectionAssemblySelector` [Section titled “IReflectionAssemblySelector”](#ireflectionassemblyselector) Used with `ISpecularProvider.GetAssemblies` and `ISpecularProvider.GetTypes`. Returns an `IReflectionTypeSelector` to continue the chain. | Method | Description | | ---------------------------------- | -------------------------------------------------------------------- | | `EntryAssembly()` | Scans the calling assembly. | | `FromAssemblies()` | Scans all metadata assemblies in the compilation. | | `FromAssemblyOf<T>()` | Scans the assembly that contains `T`. | | `FromAssemblyOf(Type)` | Non-generic overload of the above. | | `DependenciesFromAssemblyOf<T>()` | Scans the assemblies that reference the assembly containing `T`. | | `DependenciesFromAssemblyOf(Type)` | Non-generic overload of the above. | | `NotFromAssemblyOf<T>()` | Excludes the assembly containing `T` from the scan. | | `NotFromAssemblyOf(Type)` | Non-generic overload of the above. | | `IncludeSystemAssemblies()` | Also includes .NET framework / BCL assemblies (excluded by default). | ### Combining assembly selections [Section titled “Combining assembly selections”](#combining-assembly-selections) Assembly selections can be chained. They combine like this: * Several specific selections (`EntryAssembly`, `FromAssemblyOf`, `DependenciesFromAssemblyOf`) are **alternatives**: `FromAssemblyOf<A>().FromAssemblyOf<B>()` scans both assemblies, and `FromAssemblyOf<A>().DependenciesFromAssemblyOf<C>()` scans `A`’s assembly plus every assembly that references `C`’s. * `FromAssemblies()` is the starting point those narrow. On its own it scans everything; with a specific selection it adds nothing, so `FromAssemblies().DependenciesFromAssemblyOf<T>()` still means “the assemblies that reference `T`’s”. * `NotFromAssemblyOf` always excludes, whatever else selected the assembly. On its own it scans everything except that assembly. * The system assemblies (`mscorlib`, `netstandard`, `System`, `System.Core`, `System.Runtime`, `System.Private.CoreLib`) are skipped unless you call `IncludeSystemAssemblies()`. ### `IServiceDescriptorAssemblySelector` [Section titled “IServiceDescriptorAssemblySelector”](#iservicedescriptorassemblyselector) Used with `ISpecularProvider.Scan`. Has the same set of assembly-selection methods as `IReflectionAssemblySelector`, but each method returns an `IServiceDescriptorTypeSelector` to continue into the DI-specific chain. ## Type Selectors [Section titled “Type Selectors”](#type-selectors) ### `IReflectionTypeSelector` [Section titled “IReflectionTypeSelector”](#ireflectiontypeselector) Extends `IReflectionAssemblySelector`. Provides methods to retrieve `IEnumerable<Type>` directly. | Method | Description | | ------------------------------------------------ | -------------------------------------------------------------- | | `GetTypes()` | Returns all types in the selected assemblies. | | `GetTypes(bool publicOnly)` | Limits results to public types when `true`. | | `GetTypes(Action<ITypeFilter>)` | Applies a filter predicate (public non-abstract classes only). | | `GetTypes(bool publicOnly, Action<ITypeFilter>)` | Combines public-only and filter predicate. | ### `IServiceDescriptorTypeSelector` [Section titled “IServiceDescriptorTypeSelector”](#iservicedescriptortypeselector) Extends `IServiceDescriptorAssemblySelector`. Entry point for describing what to register in the DI container. | Method | Description | | -------------------------------------------------- | --------------------------------------------------------- | | `AddClasses()` | Selects all public, non-abstract classes. | | `AddClasses(bool publicOnly)` | Controls whether non-public classes are included. | | `AddClasses(Action<ITypeFilter>)` | Selects public, non-abstract classes matching the filter. | | `AddClasses(Action<ITypeFilter>, bool publicOnly)` | Filter plus public-only control. | Returns `IServiceTypeSelector` to continue the chain with a service-type strategy. ## Service Type Strategies [Section titled “Service Type Strategies”](#service-type-strategies) ### `IServiceTypeSelector` [Section titled “IServiceTypeSelector”](#iservicetypeselector) Specifies how each matched type is registered against service types. | Method | Description | | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | | `AsSelf()` | Registers each class as its own concrete type. | | `As<T>()` | Registers each class as `T`. | | `As(Type)` | Non-generic overload of `As`. | | `AsImplementedInterfaces()` | Registers each class as every interface it implements. | | `AsImplementedInterfaces(Action<ITypeFilter>)` | Same, filtered to specific interfaces. | | `AsSelfWithInterfaces()` | Registers as self **and** as every implemented interface; the interface registrations return the same singleton instance. | | `AsSelfWithInterfaces(Action<ITypeFilter>)` | Same, filtered to specific interfaces. | | `AsMatchingInterface()` | Registers each class as the interface whose name matches `I{ClassName}`. | Returns `IServiceLifetimeSelector` to complete the chain. ## Lifetime Selector [Section titled “Lifetime Selector”](#lifetime-selector) ### `IServiceLifetimeSelector` [Section titled “IServiceLifetimeSelector”](#iservicelifetimeselector) Extends `IServiceTypeSelector`.
